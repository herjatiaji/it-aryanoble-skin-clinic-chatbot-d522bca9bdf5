1. Ringkasan Eksekutif

Sistem RAG (Retrieval-Augmented Generation) saat ini telah mencapai batas kemampuan optimal (hard architectural ceiling) di atas infrastruktur server produksi yang digunakan, yaitu 2 vCPU dan 2,9 GB RAM.

Keluhan dari Product Manager (PM) mengenai "jawaban yang kaku" dan munculnya respons "Untuk saat ini informasi tersebut belum tersedia" pada pertanyaan yang memerlukan analisis relasi klinis (seperti: "apakah dermatitis boleh pakai facial DPCT?") bukan merupakan bug logika aplikasi. Hal ini adalah konsekuensi langsung dari kompromi arsitektural yang sengaja dipasang untuk mencegah container backend mengalami Out-of-Memory (OOM) Crash di server berspesifikasi sangat minim.

⚠️ Intisari Masalah Utama
Sistem saat ini berhasil dioptimalkan sebagai katalog dan SOP lookup engine berkecepatan tinggi yang super hemat memori. Namun, untuk menjadi asisten klinis analitis yang luwes, sistem membutuhkan model pemeringkat berbobot semantik (Neural Cross-Encoder) dan graf ontologi medis (GraphRAG) yang mustahil dijalankan pada alokasi memori kontainer backend sebesar 1.280 MB.

Berdasarkan konfigurasi produksi pada docker-compose.prod.yaml, total memori fisik server sebesar 2,9 GB telah dipartisi secara ketat ke seluruh microservice:

🚨 Risiko Fatal: OOM Killer
Jika alokasi RAM backend melampaui 1.280 MB, Linux Kernel OOM Killer akan langsung mengirimkan sinyal SIGKILL (Exit Code 137), merobohkan seluruh layanan chatbot seketika. Margin sisa memori sistem hanya ~436 MB, yang mutlak dibutuhkan oleh OS kernel dan file caching.

3. Bedah Kasus PM: Mengapa Pertanyaan "Dermatitis vs Facial DPCT" Gagal?

Berdasarkan keluhan PM, alur percakapan terjadi sebagai berikut:

  1. User: "kulit kering, gatal dan beruntus, apa diagnosanya" → Bot: Dermatitis.
  2. User: "apakah dermatitis boleh pakai facial DPCT?" → Bot: "Untuk saat ini informasi tersebut belum tersedia."
Alur Kegagalan Retrieval vs Safety Verification

Akar Penyebab Teknis:

  • SOP Menulis Sinonim Klinis, Bukan Nama Penyakit: Di lembar SOP resmi Facial DPCT, kolom kontraindikasi berbunyi: "lesi inflamasi akut, infeksi aktif, luka terbuka". Kata "dermatitis" tidak tertulis secara harfiah.
  • PostgreSQL FTS Menghasilkan Nilai 0: Pencarian leksikal mencocokkan kata persis. Karena tidak ada chunk yang memuat kata dermatitis dan dpct secara bersamaan, skor leksikal bernilai nihil.
  • Ketiadaan Medical Cross-Attention: RRF matematis tidak memiliki kecerdasan semantik untuk menyimpulkan bahwa Dermatitis adalah bentuk dari Lesi Inflamasi Akut.
  • Grounded Verification Gate: Pipeline anti-halusinasi bertindak sesuai protokol keselamatan medis: jika suatu kesimpulan tidak memiliki referensi teks eksplisit di potongan dokumen yang terambil, generator dilarang berspekulasi dan dipaksa memunculkan fallback aman.

6. Rekomendasi Solusi & Pilihan Strategis

💡 OPSI A (Sangat Direkomendasikan): Integrasi Cloud API Neural Reranker
Tanpa Perlu Upgrade Server Fisik (Beban RAM Lokal: 0 MB)
Sistem saat ini dapat langsung memiliki kemampuan Neural Cross-Attention setara versi terbaik dengan menghubungkan retrieval ke Cohere Rerank v3 API via HTTPS call.
  • Beban RAM Lokal: 0 MB (komputasi model berjalan di cluster Cohere).
  • Latensi Tambahan: Hanya ~100-150 ms per kueri.
  • Dampak: Langsung mengenali negasi medis dan hubungan sinonim klinis tanpa risiko OOM crash.
  • Biaya: Sangat hemat (~$1 per 1.000 pencarian).

Opsi B: Upgrade Server Menengah (Jika Harus On-Premise)

Jika data klinik tidak boleh menyentuh API pihak ketiga, ajukan kenaikan spesifikasi server ke 4 vCPU / 8 GB RAM. Hal ini memungkinkan penggunaan model reranker CPU-terkuantisasi (ONNX INT8) secara lokal dan membuka batas ingesti paralel.

Opsi C: Dedicated Enterprise AI Node (Jangka Panjang)

Menyediakan 1 node khusus dengan GPU NVIDIA L4 (24GB VRAM) khusus untuk melayani ColBERTv2 dan GraphRAG terintegrasi UMLS/SNOMED-CT bagi ekosistem rumah sakit dan klinik Arya Noble secara menyeluruh.
